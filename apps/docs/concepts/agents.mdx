`agent()` turns an LLM tool loop into a one-file definition. The framework runs the loop, streams tokens over a resumable stream, executes your tools with validated arguments, and persists every turn — user input, assistant text, tool calls, tool results — into synced entities that update live on all of the user's devices.

```ts
// functions/researcher.ts
import { agent, v } from "@pylonsync/functions";

export default agent({
  system: "You are a research assistant for this workspace.",
  tools: {
    searchDocs: {
      description: "Search the document library for relevant passages",
      args: { query: v.string() },
      handler: async (ctx, { query }) =>
        ctx.runQuery("findSimilar", { query }),
    },
    sendSummary: {
      description: "Email a summary to the signed-in user",
      args: { subject: v.string(), body: v.string() },
      handler: async (ctx, { subject, body }) => {
        await ctx.email.send(ctx.auth.userId!, String(subject), String(body));
        return { sent: true };
      },
    },
  },
});
```

That's the whole backend. The agent is a normal action named after its file — call it from the client with `streamFn`:

```ts
const gen = streamFn("researcher", { input: question }, {
  onStreamId: (id) => setLiveStreamId(id),
});
for await (const chunk of gen) append(chunk);   // token stream
const { runId } = (await gen.next()).value as { runId: string };
```

## What a run is

Every invocation creates (or continues) an **AgentRun** with an ordered **AgentMessage** transcript. Both are ordinary synced entities the framework injects into your manifest when any agent exists:

- `AgentRun` — `agent`, `status` (`idle | running | completed | failed`), `title`, `streamId` (the resumable stream of the current generation), `error`, timestamps. Owner-scoped: readable only by the user who started it.
- `AgentMessage` — `runId`, `seq`, `role`, `content` (a string for user turns; content blocks for assistant turns, including `tool_use` and `tool_result` records).

Because they're plain synced entities, everything you already know applies: they replicate into the owner's local replica live, `pylon codegen` types them, `pylon migrate` creates them on Postgres, and policies fence them (clients can never write them — the loop's server-side mutations are the only writer).

If your app declares its own `AgentRun` or `AgentMessage` entity (to add columns), yours wins — but the loop still writes through it, so keep the framework's columns intact: `AgentRun` needs `agent`, `status`, `userId`, `title`, `streamId`, `error`, `createdAt`, `updatedAt`; `AgentMessage` needs `runId`, `userId`, `seq`, `role`, `content`, `createdAt`. The same goes for policies: declaring your own `AgentRun` policy replaces the injected one, so keep reads owner-scoped with the `auth.userId != null &&` guard (bare `data.userId == auth.userId` matches anonymous callers against null-owner rows).

```tsx
import { useAgentRun } from "@pylonsync/react";

function RunView({ runId }: { runId: string }) {
  const { run, messages } = useAgentRun(runId);
  // messages update in real time as the loop persists turns —
  // in this tab, in other tabs, on the user's phone.
}
```

## Conversations

Pass `runId` to continue with full history:

```ts
for await (const chunk of streamFn("researcher", { input: followUp, runId })) {
  append(chunk);
}
```

The loop reloads the transcript, appends the new user turn, and the model sees everything — including its own earlier tool calls. A run mid-generation rejects a second turn with `RUN_BUSY` (the claim happens inside a transaction, so two simultaneous turns can't both win). A run stuck in `running` longer than the agent's `timeout` is a dead generation — the next turn takes it over. A run belonging to another user is indistinguishable from a missing one (`RUN_NOT_FOUND`).

Runs always have an owner: an unauthenticated or system caller gets `AGENT_REQUIRES_USER`. To invoke an agent from a cron job or another server-side path, run it under a service user's auth.

## Watching from another device

The transcript arrives per-message via sync. For token-level liveness, the run row records the current generation's resumable stream id:

```ts
const { run } = useAgentRun(runId);
if (run?.status === "running" && run.streamId) {
  for await (const token of resumeStream(run.streamId)) paint(token);
}
```

`resumeStream` replays the buffered tokens from the start, then live-tails — and still delivers the final result if the run finished while you were connecting.

## The stream

While generating, the SSE stream carries:

- plain data frames — the assistant's text deltas,
- `event: tool` frames — `{ name, input, isError }` as each tool executes, so a UI can render "searching docs…" without waiting for the message row,
- the terminal `event: result` — `{ runId, text, steps, usage }`.

## Tools

Tool `args` are the same `v.*` validators as functions, converted to JSON Schema for the model. The model's arguments are validated before your handler runs; invalid input, a thrown handler error, or an unknown tool all become `is_error` tool results the model can react to — a bad tool call never kills the run. Handlers get the full action ctx: `runQuery`/`runMutation` for data, `ctx.llm` for sub-calls, `ctx.email`, `ctx.workflows`, everything.

Options: `model` (subject to the server's allowlist), `maxSteps` (default 16 — hitting the cap fails the run instead of looping forever), `maxTokens`, `auth` (`"user"` default; agents require a signed-in caller so runs always have an owner), `timeout` (default 600s idle).

## Failure semantics

A provider error, a `maxSteps` overrun, or a crash marks the run `failed` with the error message on the row — visible to the UI through the same sync channel as everything else. Completed and failed runs are permanent history; start a new turn on the same `runId` to keep going after a failure. If a crash interrupted a tool call mid-flight, the next turn repairs the transcript with an `is_error` tool result ("tool execution was interrupted") so the model's history stays replayable. Tool results are capped at 64KB per result; anything longer persists with a `[truncated]` suffix.

For work that must survive a server restart mid-flight, wrap the agent call in a [workflow](/concepts/workflows) — runs are durable state, but a generation in progress lives with the process, exactly like any action.
