---
title: "Realtime Shards"
description: "Authoritative game and simulation logic in Rust, compiled to WebAssembly and run by the stock pylon binary on a fixed tick."
---

A shard is one running simulation: a match, a zone, a room. The server owns
its state. Clients send inputs, the shard applies them on its tick, and every
subscriber gets a snapshot after each tick.

You write the simulation in Rust with the `pylon-shard-guest` crate and
compile it to WebAssembly. The `pylon` binary loads the module at boot. You
do not build a custom server binary, so the same app runs on `pylon dev`,
`pylon start`, a Docker image, and Stack0 Cloud.

The complete example is [`examples/shard-arena`](https://github.com/pylonsync/pylon/tree/main/examples/shard-arena).

## Set up

Install the WebAssembly target once:

```bash
rustup target add wasm32-unknown-unknown
```

Make a library crate inside the app, for example `shards/arena`:

```toml shards/arena/Cargo.toml
[package]
name = "arena-shard"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
pylon-shard-guest = "0.13"
serde = { version = "1", features = ["derive"] }

[profile.release]
opt-level = "s"
lto = true
```

If the app is inside a Cargo workspace, add an empty `[workspace]` table so
the crate builds on its own.

## Write the simulation

Implement `Shard` and export it with `export_shard!`:

```rust shards/arena/src/lib.rs
use std::time::Duration;

use pylon_shard_guest::{export_shard, Shard};
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct Params {
    width: f32,
    height: f32,
}

#[derive(Deserialize)]
#[serde(rename_all = "snake_case")]
enum Input {
    MoveTo { x: f32, y: f32 },
}

#[derive(Serialize, Clone)]
struct Player {
    id: String,
    x: f32,
    y: f32,
}

#[derive(Serialize)]
struct Snapshot {
    players: Vec<Player>,
}

struct Arena {
    width: f32,
    height: f32,
    players: Vec<Player>,
}

impl Shard for Arena {
    type Params = Params;
    type Input = Input;
    type Snapshot = Snapshot;

    fn init(_shard_id: &str, p: Params) -> Result<Self, String> {
        Ok(Arena { width: p.width, height: p.height, players: Vec::new() })
    }

    fn apply_input(&mut self, sid: &str, input: Input) -> Result<(), String> {
        let Input::MoveTo { x, y } = input;
        if x < 0.0 || x > self.width || y < 0.0 || y > self.height {
            return Err("outside the arena".into());
        }
        match self.players.iter_mut().find(|p| p.id == sid) {
            Some(p) => (p.x, p.y) = (x, y),
            None => self.players.push(Player { id: sid.into(), x, y }),
        }
        Ok(())
    }

    fn tick(&mut self, _dt: Duration) {}

    fn snapshot(&self) -> Snapshot {
        Snapshot { players: self.players.clone() }
    }
}

export_shard!(Arena);
```

The trait has these methods:

| Method | Called | Default |
| --- | --- | --- |
| `init(shard_id, params)` | Once, from `ctx.shards.create`. An error refuses the create. | Required |
| `apply_input(subscriber, input)` | On the tick, once per queued input, in arrival order. An error goes back to the sender as an `apply_failed` rejection. | Required |
| `tick(dt)` | At the tick rate. `dt` is `1 / tickRate` with `fixedTimestep`. | Required |
| `snapshot()` | After each tick. | Required |
| `snapshot_for(subscriber)` | After each tick, per subscriber. Return `Some` for area of interest or fog of war. | `None`: the subscriber gets `snapshot()` |
| `is_finished()` | After each tick. `true` stops the shard. | `false` |
| `authorize_subscribe(subscriber, auth)` | When a client connects. | Admits an admin, a ticket holder, or a user whose id is the subscriber id |
| `authorize_input(subscriber, auth, input)` | Before an input is queued. | Admits all |

`auth` carries `user_id`, `is_admin`, `roles`, `tenant_id`, and the verified
ticket. Read ticket claims with `auth.claim("realm")`.

The module has no clock, no random source, and no I/O. Put a seed in
`params` when the game needs random numbers. The same inputs then give the
same state, which a replay needs. `pylon_shard_guest::log(Level::Info, "…")`
writes to the server log.

### Send each player only what is near them

In a large zone, return an `InterestConfig` from `interest`. Each tick the
host puts your entities in a grid, keeps the ones within each subscriber's
radius, and asks `snapshot_visible` for that subscriber's snapshot:

```rust
use pylon_shard_guest::{EntityPos, InterestArea, InterestConfig, View};

impl Shard for Zone {
    // ...
    fn interest(&self) -> Option<InterestConfig> {
        Some(InterestConfig { cell_size: 150.0, margin: 10.0, shared_snapshots: true })
    }

    fn entities(&self, out: &mut Vec<EntityPos>) {
        out.extend(self.units.iter().map(|u| EntityPos { id: u.id, x: u.x, y: u.y }));
    }

    fn interest_area(&self, sid: &str) -> Option<InterestArea> {
        let me = self.player_unit(sid)?;
        Some(InterestArea { x: me.x, y: me.y, radius: 150.0 })
    }

    fn can_see(&self, sid: &str, entity: u64) -> bool {
        !self.is_stealthed(entity) || self.can_detect(sid)
    }

    fn snapshot_visible(&self, _sid: &str, view: &View) -> Option<Snapshot> {
        Some(Snapshot { units: view.visible.iter().map(|id| self.unit(*id)).collect() })
    }
}
```

- An entity leaves view only after it is `margin` past the radius, so an
  entity at the edge does not flicker in and out.
- `can_see` hides an entity in range, for stealth or fog of war.
- `view.entered` and `view.left` list the ids that came into and went out
  of view since the last tick.
- With `shared_snapshots: true`, subscribers that see the same entities get
  one snapshot, encoded once. Use it only when `snapshot_visible` reads
  nothing but `view.visible`.
- Positions are 2D. A 3D world passes its ground plane.
- For 300 subscribers and 1,000 moving entities, the grid work takes about
  0.2 ms per tick when players are spread out, and about 1.5 ms when they
  crowd together.

A Rust shard compiled into a custom binary uses the same hooks on
`SimState`: `interest_config`, `entities`, `interest_area`, `can_see` (or
`filter_visible`), `snapshot_visible`, `shares_visible_snapshots`,
`replicated`, and `replication_config`.

### Replicate entities instead of sending snapshots

A snapshot is the whole visible state every tick. For many moving entities,
replicate them instead: keep them in a `Replicated` store, and each
subscriber gets only what changed.

```rust
use pylon_shard_guest::{Replicated, ReplicationConfig};

const HP: u8 = 1; // component ids are yours to choose

impl Shard for Zone {
    // ...
    fn tick(&mut self, dt: Duration) {
        for unit in &mut self.units {
            unit.step(dt);
            self.store.set_pos(unit.id, [unit.x, unit.y, 0.0]);
        }
    }

    fn replicated(&mut self) -> Option<&mut Replicated> {
        Some(&mut self.store)
    }

    fn replication_config(&self) -> ReplicationConfig {
        ReplicationConfig { precision: 0.01, max_bytes_per_tick: 900, y_up: false }
    }
}
```

Use the store's methods for every change: `spawn(id, [x, y, z])`,
`set_pos`, `set_component(id, component, bytes)`, `remove_component`, and
`despawn`. A change to the same value is not sent.

Each tick, each subscriber gets one frame with:

- **despawn** for entities that left its view or the store,
- **spawn** with the full state for entities that came into view,
- **update** for entities in view that changed: only the axes whose
  position moved (as a difference) and the components that changed or were
  removed.

The view is the interest view when `interest` returns a config, or every
entity otherwise. `can_see` still hides entities. `snapshot*` is not used.

| Setting | Meaning |
| --- | --- |
| `precision` | Position step in world units. Positions travel as `round(value / precision)`. |
| `max_bytes_per_tick` | Update budget per subscriber per tick. Spawns and despawns always go; updates go in priority order (the longer since the entity was sent and the nearer it is, the higher). What does not fit is sent later. `0` = no limit. |
| `y_up` | The ground plane interest management uses: `false` for x/y, `true` for x/z. |

A new connection, and one whose outbound queue dropped frames, gets a full
frame. Replication needs the shard WebSocket (`/shard`); SSE refuses a
replicating shard.

For 300 players in one area, all moving, at 20 Hz: about 23 KB/s per
client with no budget, and 15 KB/s with a 900-byte budget, where a
client's positions stay within 0.08 units of the server's at p99.

### Client: a render loop

`@pylonsync/realtime` is the client with no framework. `connectShardGame`
connects, applies each frame, and places entities for a render frame
without a React render:

```ts
import { connectShardGame } from "@pylonsync/realtime";

const game = connectShardGame<Input>(shardId, { subscriberId, ticket, tickRate: 20 });

function frame(now: number) {
  game.frame(now);
  for (const id of game.left) removeMesh(id);
  for (const id of game.entered) addMesh(id);
  for (const e of game.entities.values()) {
    moveMesh(e.id, e.x, e.y, e.z, e.components.get(HP));
  }
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

- **Interpolation.** Entities are drawn `interpolationDelayMs` (default
  100) behind the shard's current tick, between the two frames around that
  time. Spawns, despawns, and component changes show at the tick they
  happened. `e.from`, `e.to`, and `e.t` give the samples and the fraction,
  to interpolate your own data in components (a heading). An id in both
  `left` and `entered` is a new entity that reused the id.
- **The clock.** `game.clock` estimates the shard's current tick from when
  frames arrive, anchored on the least-delayed frame. Pass `tickRate` when
  you know it; otherwise it is measured.
- **Prediction.** `game.predict(step)` returns a `Predictor` that records
  each input you `send`. After each frame, `reconcile(serverState, ack)`
  starts from the shard's state for your entity and applies the inputs it
  has not processed. Refused inputs drop out, and a reconnect clears it.
- **Round trip.** `game.rttMs` is the smoothed time from an input to the
  frame that acknowledges it.
- **Reconnects** get a full frame. The entities it lacks leave.

`game.latest` is the newest table, not interpolated. `connectShard` is the
connection alone, with `onReplication` and `entities`. `useShard` in
`@pylonsync/react` re-renders on every frame; use it for small,
turn-based, or UI-only shards. In Swift, `ShardClient<NoSnapshot, Input>`
has `entities` and a `replication()` stream.

## Declare the shard kind

Add the kind to `buildManifest` in `app.ts`:

```ts app.ts
import { buildManifest, shard } from "@pylonsync/sdk";

export default buildManifest({
  // ...
  shards: [
    shard({
      name: "arena",
      wasm: "shards/arena.wasm",
      crate: "shards/arena",
      codec: "msgpack",
      tickRate: 20,
    }),
  ],
});
```

| Field | Meaning | Default |
| --- | --- | --- |
| `name` | The kind name `ctx.shards.create` takes. | Required |
| `wasm` | The module, relative to the app root. | Required |
| `crate` | A Cargo crate that `pylon shards build` compiles to `wasm`. | None |
| `codec` | `"json"` or `"msgpack"`, for inputs and snapshots. | `"json"` |
| `tickRate` | Ticks per second. `0` ticks only when inputs arrive. | 20 |
| `fixedTimestep` | Pass `tick` a constant `dt`. | `true` |
| `maxSubscribers` | Subscribers per shard. | 256 |
| `maxInstances` | Shards of this kind that may run at once. | 64 |
| `memoryMb` | Memory cap per shard. | 64 |
| `tickBudgetMs` | Time limit for one tick (inputs, `tick`, snapshots), or for one authorize call. | 100 |
| `idleShutdownSecs` | Stop a shard with no subscribers after this long. `0` never stops it. | 90 |
| `input` | `ratePerSec`, `burst`, `maxQueued`, `maxPerTick` per subscriber. | 120, 240, 256, 32 |

## Build the module

```bash
pylon shards build
```

The command runs `cargo build --release --target wasm32-unknown-unknown` for
each kind with a `crate`, and copies the module to its `wasm` path.
`pylon dev` runs the same build at start. It builds again and restarts the
server when a `.rs` file or `Cargo.toml` in the crate changes.

Commit the `.wasm` file. `pylon build` copies it into the artifact, and
`pylon deploy` uploads it even when `.gitignore` lists it. When `cargo` is on
the path, `pylon deploy` builds the crates first. A GitHub deploy uses the
committed file, because the Cloud builder has no Rust toolchain.

## Start a shard and join it

An action starts a shard and gives the player a ticket:

```ts functions/joinArena.ts
import { action } from "@pylonsync/functions";

export default action({
  args: {},
  async handler(ctx) {
    const id = "arena-main";
    if (!(await ctx.shards.get(id))) {
      await ctx.shards.create("arena", id, { width: 800, height: 500 });
    }
    const ticket = await ctx.shards.ticket(id);
    return { shardId: id, subscriberId: ctx.auth.userId, ticket };
  },
});
```

`ctx.shards` has these calls:

| Call | Result |
| --- | --- |
| `create(kind, id, params)` | Starts shard `id`. Throws `SHARD_EXISTS`, `SHARD_LIMIT_REACHED`, `SHARD_KIND_NOT_FOUND`, `SHARD_ID_INVALID`, or `SHARD_INIT_FAILED`. Actions only. |
| `stop(id)` | Stops the shard and closes its connections. Actions only. |
| `get(id)` | `{ id, kind, tick, subscribers, running, error? }`, or `null`. |
| `list()` | Every running shard. |
| `ticket(id, opts)` | A signed ticket. See [shard tickets](/concepts/functions#shard-tickets). |

A shard id is 1 to 128 letters, digits, `-`, `_`, `.`, or `:`.

The client connects with the ticket:

```tsx
import { useShard } from "@pylonsync/react";

const { snapshot, send, lastRejection } = useShard<Snapshot, Input>(shardId, {
  subscriberId,
  ticket,
});

send({ move_to: { x: 120, y: 80 } });
```

The client connects to `/shard` on the app's own origin, so it needs no
extra port or proxy rule. See [React client](/clients/react#multiplayer-shards)
for acks, rejections, and custom decoders.

## Load test

`pylon bench shard` starts headless bots that join like players, send
inputs, and decode every frame:

```bash
pylon bench shard --join joinArena --bots 300 --duration 30 --rate 10 \
  --input '"join"' \
  --input '{"move_to":{"x":"$rand:0:800","y":"$rand:0:500"}}'
```

- `--join <function>` signs each bot in as a guest and calls the function,
  which returns `{ shardId, subscriberId, ticket }`.
- `--shard <id>` joins a running shard with tickets the command mints. Run it
  from the app directory, so it uses the same key as `pylon dev`, or set
  `PYLON_SHARD_TICKET_SECRET` to the server's value.
- `--input` is a JSON template, and repeated templates are sent in turn. The
  strings `"$rand:A:B"`, `"$int:A:B"`, `"$bot"`, and `"$sid"` are replaced
  for each input.
- `--url` defaults to `http://localhost:4321`. An `https://` origin connects
  over `wss://`.

The report gives:

| Line | Meaning |
| --- | --- |
| tick rate seen | New ticks per second each bot received |
| snapshot interval | Time between frames at a bot (p50, p99, max) |
| input to ack | Time from sending an input to the first frame that acks it |
| bytes per bot | Bytes each bot received per second |
| rejections | Refused inputs, by code |

`pylon dev` lifts the per-IP connection cap. Against `pylon start`, set
`PYLON_SHARD_WS_MAX_PER_IP=0` on the server when all bots run on one
machine.

To run bots from several machines, give each machine its own
`--bot-offset` and `--report <file>`, then combine the reports:

```bash
pylon bench shard ... --bots 300 --bot-offset 0   --report a.json   # machine 1
pylon bench shard ... --bots 300 --bot-offset 300 --report b.json   # machine 2
pylon bench merge a.json b.json
```

## Limits and failures

- A tick that runs past `tickBudgetMs` stops the shard.
- A module that grows past `memoryMb` stops the shard.
- A panic stops the shard. The server log shows the panic message.
- `ctx.shards.get(id)` returns the reason in `error` until the host removes
  the stopped shard (within a few seconds).
- A module may import only `pylon.log`. The server refuses a module built for
  WASI or with any other import, and the boot fails.
- Shard state is in memory. A restart or a deploy ends every shard.

## Hosted on Stack0 Cloud

[Stack0 Cloud](/cloud) runs shards with no extra setup. Clients connect to
`wss://your-app.stack0.app/shard`, or to `/shard` on your custom domain.

- An open shard connection keeps the app's machine running.
- A machine with autostop on can stop when no client is connected. Its
  shards end, like on any restart.
